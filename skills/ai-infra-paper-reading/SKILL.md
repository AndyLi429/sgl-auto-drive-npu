# AI Infra Paper Reading

把论文结论还原为一条可核对的因果链：**哪个瓶颈存在，方案改变了什么机制，为什么该机制会改变指标，以及代价转移到了哪里。** 不把摘要中的主张、实验观察和自己的推断混为一谈。

## 输入与证据边界

先确认论文的标题、版本、来源和用户的阅读目标。优先读取用户提供的 PDF、链接、正文、补充材料和代码；若只给出标题或摘要，先说明证据不足，只输出可确认内容与待核验问题。处理本地 PDF 时，使用 `pdf` Skill 获取正文、图表和页码。

给关键结论附上最小可追溯证据：`§章节`、`图 N`、`表 N`、页码或原文链接。使用以下标签：

- **[论文证据]**：论文直接陈述或测量的内容。
- **[用户材料]**：用户给出的标题、摘要或转述；除非能定位到论文原文，否则不等同于论文证据。
- **[推断]**：由设计和数据推出的解释，说明推断依据。
- **[待验证]**：论文没有报告、证据互相矛盾或无法从现有材料确认的内容。

除非论文实际比较过，否则不要把某个系统写成“优于”另一个系统；不要把吞吐改善自动解释为尾延迟改善，也不要把端到端加速归因给单个 kernel。

## 三遍阅读：先定位，再核查，再重建

按斯坦福三遍论文阅读法组织工作，但可根据用户时间预算缩放深度。

| 遍次 | 要回答的问题 | 阅读重点 | 产物 |
|---|---|---|---|
| 第一遍：定位 | 为了什么问题、提出什么方法、实现什么效果？ | 标题、摘要、引言、贡献、图表标题、结论、参考文献 | 一句话总结、论文类别、适用工作负载、3 个核心主张与待验证清单 |
| 第二遍：核查 | 设计和评测是否支撑这些主张？ | 系统总览、关键图表、表格、实验设置、baseline 与消融 | 机制图、评测对照表、因果链草案、可疑比较或缺失变量 |
| 第三遍：重建 | 如果自己实现，状态、控制路径和成本会怎样流动？ | 算法细节、实现、附录、证明、失败案例、代码（若有） | 从瓶颈到指标的完整解释、局限、复现实验要点和工程启发 |

## AI Infra 性能链路

按下面顺序检查论文，但每一项都标为 **主瓶颈**、**受影响**、**不涉及** 或 **证据不足**；不要为了完整性强行填满。“不涉及”只用于材料明确排除的环节；材料不足时标“证据不足”。

```text
模型计算 → KV Cache → batching → scheduling → parallelism → communication
        → memory → kernel → hardware utilization → serving metrics
```

对标为主瓶颈或受影响的环节，记录：

| 环节 | 要找的事实 | 必须追问的因果问题 |
|---|---|---|
| 模型计算 | prefill/decode、attention、MoE 或多模态的计算形态 | 改的是 FLOPs、计算重叠，还是计算出现的时机？ |
| KV Cache | 布局、量化、复用、迁移、淘汰与命中率 | 节省的容量、带宽或重算，是否以精度/复制成本交换？ |
| batching / scheduling | 请求合并规则、抢占、chunking、优先级 | 改善来自更高并发、减少等待，还是工作负载选择偏差？ |
| parallelism / communication | TP/PP/EP、分片、collective、网络拓扑 | 通信是否被隐藏、减少或只是挪到别处？ |
| memory / kernel | 访存路径、数据布局、融合、图编译 | 是否降低 HBM 流量、launch 开销或同步，而非仅优化计算？ |
| hardware utilization | SM/NPU 利用率、带宽、算力、空泡 | 利用率指标的口径、采样方式和硬件上限是什么？ |
| serving metrics | TTFT、TPOT、吞吐、p50/p99、成本、SLO | 指标定义、负载分布、并发、输入/输出长度是否公平一致？ |

当论文跨硬件、框架或模型比较时，单列不可比因素：精度、batch/concurrency、上下文与生成长度、模型版本、节点数、互连、软件版本、warm-up、请求到达过程和 SLO。NPU、GPU 或具体框架的结论只能写到论文实际测量的边界。

## 报告交付

读取 [references/reading-report-template.md](references/reading-report-template.md)，按其结构输出中文 Markdown。默认先给不超过三句的结论，再给八部分报告。报告必须包含：

1. 主要创新 IDEA 与其解决的问题；
2. “问题 → 方法 → 效果”的三遍阅读结论；
3. 至少一张 Mermaid 因果图，展示论文实际涉及的性能链路；
4. 评测环境、baseline、metric 和主要结果；
5. 明确区分论文证据、推断与待验证项；
6. 面向当前工作（例如 SGLang / NPU serving）的可执行启发，而不是泛泛的“值得学习”。

Mermaid 图只呈现有证据的节点和边；使用安全的英文节点 ID，并给含特殊字符的标签加双引号。若没有渲染器，做静态语法检查并说明未渲染。

## 常见误读

| 误读 | 正确处理 |
|---|---|
| 摘要说“加速”，就断言所有请求都更快 | 分开写 TTFT、TPOT、吞吐和尾延迟，并保留工作负载条件。 |
| 只列机制，不解释指标为何变化 | 填写“瓶颈 → 干预 → 机制 → 指标 → 代价”的因果账本。 |
| 把图中的利用率当作端到端收益 | 查找利用率的采样窗口，并与服务指标和瓶颈变化交叉验证。 |
| baseline 名称相同就默认公平 | 核对模型、硬件、并发、长度分布、精度和软件栈。 |
| 把没讨论的限制写成论文结论 | 标为 [推断] 或 [待验证]，并说明原因。 |
